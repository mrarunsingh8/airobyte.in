# Node.js Architecture
## The Main Layers

The Node.js architecture can be understood from the top down:

```text
Your application code
        |
Node.js core APIs and modules
        |
Node.js bindings
        |
V8 JavaScript engine       libuv library
        |                         |
        +------ Operating system-+
```

Each layer has a different responsibility. Together, they allow JavaScript code to work with files, networks, processes, timers, and other system resources.

## 1. Application Code

This is the code developers write. It contains the application's routes, business rules, database calls, and response handling.

For example, an application can create an HTTP server using the built-in `node:http` module:

```js
const http = require("node:http");

const server = http.createServer((request, response) => {
  response.end("Hello from Node.js");
});

server.listen(3000);
```

The application code does not need to implement TCP connections or operating-system calls itself. It uses the APIs provided by Node.js.

## 2. Node.js Core APIs

Node.js exposes JavaScript APIs for common server and system tasks. Important core modules include:

- `node:http` for HTTP servers and requests
- `node:fs` for reading and writing files
- `node:path` for safely working with file paths
- `node:crypto` for cryptographic operations
- `node:events` for event-based communication
- `node:stream` for processing data piece by piece
- `node:process` for environment and process information

These APIs provide a consistent JavaScript interface, while the lower layers handle the platform-specific work.

## 3. V8 JavaScript Engine

**V8** parses, compiles, and executes JavaScript. It manages the JavaScript call stack and memory, and it uses just-in-time compilation to optimize frequently executed code.

V8 is responsible for JavaScript language features such as:

- Variables and functions
- Objects and classes
- Promises and async functions
- The call stack
- Memory management and garbage collection

V8 does not provide Node.js features such as file access or HTTP servers. Node.js connects V8 to those capabilities through its own APIs.

## 4. Node.js Bindings

Node.js bindings connect JavaScript APIs to native code written mainly in C and C++. When application code calls a module such as `node:fs`, the binding passes the request from the JavaScript layer to the native Node.js implementation.

Bindings hide platform-specific details from application developers. The same JavaScript API can work on macOS, Windows, and Linux even though the operating-system calls underneath are different.

## 5. libuv

**libuv** is a cross-platform library used by Node.js for asynchronous I/O and the event loop. It helps Node.js work with:

- File-system operations
- Network connections
- Timers
- DNS lookups
- Some operations that use a worker thread pool

When an asynchronous operation is started, libuv and the operating system can handle the waiting work while the main JavaScript thread continues running other code.

## 6. The Asynchronous Boundary

The event loop is the mechanism that schedules ready callbacks, but this lesson focuses on the boundary between the runtime layers. Application code calls a JavaScript API, Node.js bindings pass the request to native code, and libuv coordinates the operating-system work.

The event-loop lesson explains the phases, timers, and callback ordering in detail. Keeping that scheduling topic separate makes this layered architecture easier to understand.

## 7. The Operating System

The operating system provides the lowest-level resources: files, sockets, timers, processes, threads, and network interfaces. Node.js does not replace the operating system. It provides a portable JavaScript interface for using those resources.

For example, when a server listens on port `3000`, the operating system manages the network socket while Node.js manages the JavaScript callback that handles each request.

## What Happens During a File Read?

Consider this code:

```js
const fs = require("node:fs");

fs.readFile("notes.txt", "utf8", (error, contents) => {
  if (error) throw error;
  console.log(contents);
});

console.log("The read has started.");
```

The architecture handles it like this:

1. The application calls `fs.readFile`.
2. The Node.js `fs` API passes the request through a native binding.
3. libuv and the operating system perform the file operation.
4. JavaScript continues and prints `The read has started.`
5. When the file is ready, Node.js schedules the callback.
6. The callback runs and prints the file contents.

## Why This Architecture Matters

The layers give Node.js a useful balance:

- JavaScript keeps application code productive and approachable.
- V8 executes JavaScript efficiently.
- Core APIs expose server and operating-system capabilities.
- libuv coordinates asynchronous work across platforms.
- The operating system performs the low-level resource operations.

Understanding these layers also explains Node.js limitations. I/O operations can run asynchronously, but CPU-heavy JavaScript still occupies the main thread and can delay every other callback.

## Key Takeaways

- Application code uses Node.js core APIs to perform server and system tasks.
- V8 executes JavaScript and manages the JavaScript runtime.
- Native bindings connect JavaScript APIs to platform-specific implementations.
- libuv provides the event loop and helps coordinate asynchronous I/O.
- The operating system manages files, sockets, timers, processes, and other resources.
- The architecture is efficient for I/O-heavy work, but CPU-heavy code can block the main event loop.
