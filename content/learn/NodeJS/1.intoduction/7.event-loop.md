# The Node.js Event Loop

> The event loop in Node.JS allows non-blocking io operations by offloading task to the system kernal. The kernal handles multiple operations in the background and notify Node.JS when they are complete, so the appropriate callback can be executed.

The event loop in Node.js enables non-blocking I/O by allowing the operating system and libuv to handle waiting work in the background. When an operation completes, Node.js schedules its callback to run.

## How the Event Loop Works

The event loop continuously checks for ready callbacks and runs them when the call stack is empty. A simplified cycle is:

1. Run the current JavaScript.
2. Process timer callbacks.
3. Process ready I/O callbacks.
4. Process `setImmediate()` callbacks in the check phase.
5. Repeat while work remains.

For example, a server may need to wait for a file, database, or network response. Instead of waiting doing nothing, Node.js can start that operation and run other JavaScript while it waits.

## A Simple Picture

Think of a restaurant:

- The **JavaScript thread** is the waiter taking orders.
- A slow task, such as reading a file, is sent to the kitchen.
- The **event loop** checks which orders are ready.
- When an order is ready, the waiter delivers it to the customer.

The waiter does not stand in the kitchen waiting for one order. That is how Node.js can keep responding while I/O operations are in progress.

## JavaScript Runs One Piece at a Time

Node.js runs JavaScript on one main thread by default. The call stack runs one piece of JavaScript at a time.

```js
console.log("First");
console.log("Second");
console.log("Third");
```

The output is always:

```text
First
Second
Third
```

The event loop does not make two JavaScript statements run at exactly the same time. It helps schedule work so the main thread does not remain stuck waiting for I/O.

## Synchronous and Asynchronous Work

Synchronous code finishes before the next line runs:

```js
console.log("A");
console.log("B");
```

Asynchronous code starts work and calls a callback later:

```js
const fs = require("node:fs");

fs.readFile("message.txt", "utf8", (error, contents) => {
	if (error) throw error;
	console.log("File contents:", contents);
});

console.log("The file read has started.");
```

The file operation may take time, so Node.js can print `The file read has started.` before printing the file contents. The callback runs when the file is ready and the event loop can run it.

## The Main Event Loop Phases

The event loop moves through phases. Each phase has a queue of callbacks that are ready to run.

The most useful phases to know are:

1. **Timers:** Runs callbacks for `setTimeout()` and `setInterval()` when their time threshold has been reached.
2. **Pending callbacks:** Runs some callbacks postponed from an earlier loop cycle.
3. **Poll:** Receives new I/O events and runs most I/O callbacks.
4. **Check:** Runs `setImmediate()` callbacks.
5. **Close callbacks:** Runs callbacks for closed sockets and other handles.

The internal `idle` and `prepare` phases are used by Node.js and are usually not important when writing application code.

## Timers Are Minimum Delays

The delay passed to `setTimeout()` is a minimum threshold, not a promise that the callback will run at that exact time.

```js
setTimeout(() => {
	console.log("Timer finished");
}, 0);

console.log("Synchronous code finished");
```

The output is:

```text
Synchronous code finished
Timer finished
```

Even with a delay of `0`, the timer waits until the current synchronous code has finished. A busy callback or a busy operating system can delay it further.

## `setImmediate()` and `setTimeout()`

These functions are similar, but they are designed for different situations:

- `setTimeout()` runs after at least the requested time has passed.
- `setImmediate()` runs during the check phase, after the poll phase.

When both are called from the main script, their order can vary because it depends on timing. Inside an I/O callback, `setImmediate()` runs before a `setTimeout()` with a zero delay:

```js
const fs = require("node:fs");

fs.readFile(__filename, () => {
	setTimeout(() => console.log("timeout"), 0);
	setImmediate(() => console.log("immediate"));
});
```

The output is:

```text
immediate
timeout
```

## `process.nextTick()`

`process.nextTick()` is special. It is not one of the event loop phases. Node.js runs its callbacks after the current operation finishes and before the event loop continues to its next phase.

```js
console.log("Start");

process.nextTick(() => {
	console.log("nextTick");
});

console.log("End");
```

The output is:

```text
Start
End
nextTick
```

Use `process.nextTick()` carefully. Repeatedly adding more `nextTick()` callbacks can prevent the event loop from reaching I/O work. This is called **starving the event loop**.

For many normal scheduling tasks, `setImmediate()` is easier to understand because it allows the event loop to continue before running the callback.

## When Does Node.js Stop?

Node.js keeps running while it has active work, such as:

- A server listening for connections
- A timer waiting to run
- A file or network operation in progress

When there is no active work left, the event loop finishes and the process exits.

## CPU-Heavy Code Can Still Block Node.js

The event loop helps with waiting, but it cannot make a long JavaScript calculation disappear. This loop blocks the main thread:

```js
for (let number = 0; number < 1_000_000_000; number += 1) {
	// CPU-heavy work
}
```

While this code runs, other callbacks must wait. CPU-heavy work may need worker threads, child processes, or a separate service so the main event loop remains responsive.

## Key Takeaways

- The event loop helps Node.js handle asynchronous I/O without blocking on every wait.
- JavaScript still runs one piece at a time on the main thread by default.
- The loop moves through phases such as timers, poll, check, and close callbacks.
- Timer delays are minimum thresholds, not exact execution times.
- `setImmediate()` runs in the check phase, while `process.nextTick()` runs before the loop continues.
- Too much synchronous or CPU-heavy work can block every other callback.
